# Отчет об использовании AI-ассистентов (AI Review)

В ходе проектирования, отладки и стабилизации локального контура мониторинга активно использовался AI-трансформер в режиме интерактивного парного программирования (Pair Programming). Итоговая архитектурная целостность, сетевая безопасность и работоспособность решения были полностью верифицированы кандидатом.

## 1. Использованные AI-инструменты и типы промптов

* **Инструмент:** Крупная языковая модель (LLM) с поддержкой мультимодального анализа контекста терминала.
* **Основные задачи:** Генерация шаблонов Docker Compose, написание асинхронного Python-кода для Dagger SDK, интерпретация низкоуровневых логов ошибок ядра Linux и Docker-демона.
* **Применяемые промпт-стратегии:**
  * *Role-playing*: "Действуй как Senior DevOps Engineer, специализирующийся на автоматизации CI/CD через Dagger.io и мониторинге Linux-систем".
  * *Chain-of-Thought (Пошаговый анализ)*: Передача сырого лога ошибки терминала (StackTrace) с требованием объяснить физическую причину отказа перед предложением патча кода.

---

## 2. Разбор ошибок, устаревших и неоптимальных решений AI

В процессе совместной работы AI неоднократно предлагал некорректные, устаревшие или неоптимальные решения, вызванные сетевой изоляцией песочницы Dagger и спецификой modern Linux (Arch Linux). Ниже приведены 5 ключевых примеров, которые были обнаружены и исправлены кандидатом.

### Пример 1: Использование устаревшего глобального API в Dagger Python SDK
* **Что предложил AI:** Для создания базового окружения автоматизации внутри Dagger-модуля AI сгенерировал код вида `dagger.container().from_("image")`.
* **Как обнаружил проблему:** Команда `dagger call` упала с ошибкой: `FunctionError: module 'dagger' has no attribute 'container'`.
* **Как исправил:** Кандидат проанализировал изменения в современной архитектуре Dagger SDK и переписал вызовы Core API через точку входа текущего сеанса — `dagger.dag.container()`.

### Пример 2: Игнорирование контекста папок за пределами `.dagger` (Ограничение контекста)
* **Что предложил AI:** AI предложил передавать директорию проекта как аргумент функции `up(src: dagger.Directory)` и переходить в папки через `.with_workdir("/src/app-db")`.
* **Как обнаружил проблему:** Контейнер автоматизации падал с ошибкой `stat /src/app_db/docker-compose.yml: no such file or directory`. Шаг `ls -la /src` показал, что директория пуста. Это произошло потому, что AI забыл, что параметр `"source": ".dagger"` в `dagger.json` изолирует контекст и не пускает соседние папки.
* **Как исправил:** Кандидат перенес `dagger.json` в корень проекта, выставил `"source": "."`, перестроил структуру исходного кода модуля под стандарт `src/kuma_monitor/main.py` и исправил опечатку в названии папки (сменил дефис на реальное нижнее подчеркивание `app_db`).

### Пример 3: Попытка DinD-монтирования конфигурационных файлов через хостовый сокет
* **Что предложил AI:** Для настройки Prometheus AI прописал стандартный маппинг физического файла с хоста: `- ./prometheus.yml:/etc/prometheus/prometheus.yml:ro`.
* **Как обнаружил проблему:** Контейнер Prometheus падал на этапе инициализации рантайма с ошибкой: `failed to create shim task: OCI runtime create failed: error mounting "/src/observability/prometheus.yml" to rootfs...`. Причина: хостовый Docker-демон через сокет искал файл на физическом диске хоста по пути `/src/...`, который существовал только внутри временного контейнера Dagger.
* **Как исправил:** Кандидат применил более элегантное, автономное и переносимое production-решение: полностью отказался от монтирования файлов с хоста, переписав запуск Prometheus через кастомный `entrypoint` с инлайн-генерацией (`cat << 'EOF'`) конфигурации прямо в момент старта контейнера.

### Пример 4: Падение cAdvisor из-за несовместимости с cgroups v2 (Специфика Arch Linux)
* **Что предложил AI:** AI сгенерировал стандартный манифест cAdvisor со стандартными readonly-томами, применимый для cgroups v1 (Ubuntu/Debian прошлых лет).
* **Как обнаружил проблему:** Контейнер cAdvisor на Arch Linux циклически падал при старте, не отдавая метрики и не создавая порты. На дистрибутивах семейства Arch Linux используется современная cgroups v2, требующая повышенных привилегий для доступа к системным счетчикам ядра.
* **Как исправил:** Кандидат модифицировал манифест Compose Слоя 2, добавив в сервис `cadvisor` параметры `privileged: true` и проброс хостового устройства `devices: - /dev/kmsg`.

### Пример 5: Ошибка сетевой изоляции `Connection refused` при вызове REST API Grafana
* **Что предложил AI:** В команде `configure-grafana` AI сгенерировал вызов `curl` к `http://localhost:3005`, а затем попытался использовать шлюз `http://docker.internal` и прямой IP моста `172.17.0.1`.
* **Как обнаружил проблему:** Утилита `curl` падала по таймауту с ошибкой `Failed to connect / No route to host (Errno 113)`. Встроенный фаервол Arch Linux блокировал трафик к шлюзу `docker0` из изолированных подсетей Dagger Engine.
* **Как исправил:** Кандидат отверг неоптимальные варианты манипуляций с системным фаерволом хоста и переписал метод `configure_grafana`. Теперь Dagger запускает временный контейнер `curl` прямо внутри целевой пользовательской сети `kuma-shared-network`, обращаясь к API Grafana нативно и безопасно по её внутреннему DNS-имени сервиса `http://grafana:3000`.

## Заключение
Использование AI позволило значительно сократить время на написание рутинного бойлерплейт-кода манифестов. Однако финальная стабилизация контура мониторинга потребовала от кандидата глубоких фундаментальных знаний сетевой подсистемы Docker, механизмов ядра Linux (cgroups v2) и актуальной архитектуры Dagger SDK.
